# Runtime registries, routing, budgets, and artifacts

This phase adds product-neutral control-plane contracts. Consuming applications still
own provider credentials, model catalog choices, prompts, workflows, authorization
composition, and production persistence.

## Model routing

`ModelRouter` resolves a capability and complexity to a registered model identifier.
It evaluates every candidate through the central `PolicyEngine`, fails closed when no
route is explicitly allowed, and never creates a provider client or handles a secret.
The host maps the returned provider/model identifiers to its server-side adapters.
Routes also declare data locality. A `local_only` resolution considers only local
routes and fails closed when none are policy-approved; it never silently falls back
to a cloud provider. Region-restricted requests accept an explicitly matching region
or a local route.

`resolve_candidates()` returns all compatible, policy-approved routes in priority
order for a trusted host that explicitly enables failover. `FailoverModelProvider`
revalidates locality and tries the next route only when an adapter raises a specifically
configured transient exception on the initial call. Catch-all `Exception` fallback is
rejected. Once a response has established provider state—or tool results need to be
continued—the route is pinned and any failure is propagated instead of replaying work
through another provider. Candidates must come from the router; constructing a route
record is not evidence of policy approval.

`ModelCapabilities` separately describes technical provider/model behavior such as
context size, output limits, native tool support, structured output, modalities, and
locality. It does not grant tools, permissions, memory access, or delegation rights.
Gemini and Ollama adapters disable/avoid SDK-owned tool execution and return only
normalized `ToolCall` proposals to the existing central agent loop. Text-only models
receive no tool schemas and provider-returned calls are ignored.

## Budgets

`BudgetEngine` accounts for input/output tokens, tool calls, cost, and jobs at run,
job, agent, user, tenant, and tenant-day scopes. Trusted identity is supplied through
`BudgetContext`. Crossing a limit never succeeds merely because a policy returns a
plain `allow`: policy must explicitly request a bounded model-tier degradation,
approval, or review; otherwise the result is denied. A degradation outcome does not
consume the rejected estimate: the caller must select an allowed tier and submit the
new bounded estimate again.

In-memory and SQLite stores are reference implementations. SQLite survives a process
restart and reserves all applicable scopes in one `BEGIN IMMEDIATE` transaction, so
multiple local workers sharing the database cannot overspend through a check/write
race. Deployments spanning multiple database nodes still require a distributed
reservation adapter. `BudgetStore.reserve` is the atomic extension point; custom
stores must not implement it as separate read and write operations.

## Prompt and skill registries

Prompt and skill definitions are immutable and versioned. Prompt rendering accepts
only exact, simple declared variables, and `PromptRunRecord` captures the prompt,
model, toolset, policy, and memory-policy versions needed for later evaluation.

Skills contain declarative task templates rather than executable code. Compilation
produces the existing `TaskGraph`; the Task Runtime remains the only execution
authority. Step dependencies are validated as a DAG, and required tools and
capabilities are explicit metadata for host policy and worker composition. Product
workflows and prompt text do not belong in this repository.

## Artifacts

`ArtifactManager` keeps large results outside conversation messages. Artifact IDs and
storage references are generated by the runtime, ownership comes from trusted tenant
and user context, reads are owner-scoped, content is size-limited and checksummed, and
expired records are hidden and removed. The included in-memory store is a reference;
production consumers provide object storage and durable metadata through
`ArtifactStore`; an adapter may replace the logical storage reference while protected
ownership, size, and checksum fields are revalidated. Successful creation emits the
existing `artifact.created` event.

## Capability manifests

`CapabilityManifest` is an immutable, versioned, read-only description of an agent's
tools, memory namespaces, knowledge sources, model tiers, delegates, and semantic
client actions. It is suitable for admin inspection and subset checks, but it is not
an authorization decision. Runtime policy, tool permissions, approvals, and
idempotency remain authoritative.
